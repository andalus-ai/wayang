# Architecture

## Layers

```
 Studio / API (not part of this repo)
        |  definitions (Map/YAML)
        v
 wayang-business-process  wayang-dmn  wayang-integration  wayang-agent        <- definitions + validation
        |  compile
        v
 ExecutionPlan  (acyclic, engine-neutral)
        |
        +--> wayang-runtime: NodeRunner + handlers (+ ReferenceEngine for tests/demos)
        |      +--> wayang-embed: a published bundle run standalone or as a small HTTP service (production releases)
        |             ^ generated by wayang-publish from a project's published versions (docs/RELEASE.md)
        |
        +--> wayang-gamelan-worker: WorkflowDefinition + executors + GamelanReleaseEngine (no api-core; used by GAMELAN releases)
        +--> wayang-adapter-gamelan: GamelanRunEngine for the design-time server (durable execution)
        +--> wayang-adapter-andalus: AgentInvoker + node catalog       (agent execution)
```

## Process semantics

- One Wayang element = one Gamelan node of type `TASK`; `executorType` picks the Wayang executor:
  `wayang-bpmn` (events, gateways, timers, message waits), `wayang-dmn`, `wayang-eip`,
  `wayang-agent`, `wayang-human`, `wayang-service` (or an `executorType` override in the element config).
- The complete `PlanNode` (flows, conditions, config) rides in the node configuration, so executors hold no state.
- **Active/dead paths.** A node is *active* if any incoming flow is live (a parallel gateway: all of them).
  Inactive nodes emit `active=false` and all outgoing flows dead, without doing work. Exclusive gateway:
  first matching condition in order, else the default flow, else the run fails. Inclusive gateway: every
  matching flow, else default. Parallel gateway: all flows.
- Variables: a node's outputs are workflow variables `<nodeId>.<key>` (confirmed in Gamelan's
  `WorkflowRun.completeNode`). Expressions see them nested (`score.value`), process inputs as given.
- Not supported (rejected by validation): cycles/loops, sub-processes, boundary events, multi-instance.

## Waits (human tasks, timers, messages)

Gamelan's `DefaultWorkflowRunManager` completes a node only for a `COMPLETED` result; any other status
(including `WAITING`) goes through `failNode`. Wayang therefore parks a wait as an executor call that
completes later (`PendingWaits`, completed with `WayangRuntime.completeWait(token, outputs)`).

What is durable and what is not:
- **Tickets** live in a `WaitRegistry` (SPI). `register` is idempotent per run+node, so when a node is
  re-dispatched (restart, retry) it re-attaches to its existing ticket instead of creating a duplicate human
  task/timer. Provide a durable shared implementation in production; `InMemory` is for tests/demos.
- **Timers** carry `dueAt` (`duration` ISO-8601 or `until`); `TimerService.fireDue()` completes due ones and must be
  called from a scheduler. **Messages** are correlated by name + key; a message that arrives before the
  wait is buffered (bounded) and consumed when the node parks.
- `completeWait` completes the parked call first and forgets the ticket second, so a failed attempt after a
  restart keeps the ticket for the re-dispatched node.
- The **parked executor call itself** is still in the memory of the executor JVM, and relies on the
  engine/transport not timing out a long-running call. Not verified against a live engine.
- A durable alternative is run-level suspend/resume (`WorkflowRunManager.suspendRun/resumeRun`), which
  suspends the *whole* run including parallel branches. Not implemented.

## Retries, timeouts and error handling

Per-element configuration (validated when the process is compiled, see `NodePolicy`):

| Key | Meaning |
|---|---|
| `retries` | Extra attempts (0..10, default 0). Service, agent and EIP tasks only. Mapped to Gamelan's `RetryPolicy` |
| `retryDelay`, `retryMaxDelay`, `retryBackoff` | ISO-8601 durations and a multiplier (defaults PT1S, PT5M, 2.0) |
| `timeout` | ISO-8601 limit per attempt, mapped to the node timeout |
| `onError` | `fail` (default) or `continue` |

Facts about the engine that shaped this (read from `WorkflowRun`, and exercised by `GamelanRetryConformanceTest`):
- Gamelan retries **every** failure (it ignores `retryableExceptions`), so retries are opt-in: make connector calls idempotent first.
- A failed node that is not retried fails the run when the node is `critical`. A *non-critical* failed node does
  not help: its dependents are never scheduled and the run ends as `WORKFLOW_STUCK`. Wayang therefore keeps
  every node critical and implements `onError: continue` in the executor: on the **last** attempt a failure becomes a
  completed node with `failed=true` and `error=<message>` (and `failed=false` on success), so gateway
  conditions can route on `<node>.failed`. Earlier attempts still go through the engine's retry policy.
- Routing errors (an exclusive gateway with no matching flow) always fail the run; `onError` is not allowed on gateways.

## Expression language

FEEL-flavoured, all numbers `BigDecimal`, three-valued logic. Deliberate deviations: backticks for
names with spaces; `==`, `&&`, `||` aliases; `"a" + 1` concatenates; `replace`/`split` are literal, not regex;
`//` line comments. Limits: source 10k chars, depth 64, 200k evaluation steps.

## Known gaps / next steps

- `AgentSpec` -> Andalus `AgentDefinition` registration (the agent must already exist in Andalus by id).
- Durable idempotency store and wait registry implementations.
- Run the JDBC registry against a real database, and add a scheduler bean that calls `fireDueTimers()`.
- DMN XML import/export (BPMN 2.0 XML is supported for the subset in `BpmnXml`; no diagram interchange/layout on export).
- Compensation, sub-processes, boundary events, error events/error-specific routing (only `onError: continue` exists).
- Gamelan engine caveats: the SDK drops run labels (starter kept in memory only), exposes no event stream (events come from polling runs started by this instance), and parks waits in the executor JVM (completion from another node returns false). Decisions/agents resolve to the latest published version at execution time, not run start.
- Message buffer is not tenant-namespaced (a buffered message can be consumed by another tenant's waiter with the same name+key).
- Flutter web cannot send an Authorization header on WebSocket upgrade: needs a short-lived ticket endpoint. gRPC needs grpc-web for Flutter web.
- No audit log, rate limiting or pagination cursors on the API yet.
